# lhg-sa-audit：招生官视角自检流程

> 目标：提交前，用招生官的眼睛把稿子看最后一遍。
> 核心纪律：**先跑脚本（机器），再做评审（人）；blocker 不清零，不许说写完了。**

## 1. 何时使用

- 终稿完成、提交前 → 跑全流程
- 只想快速看一眼 → 只跑第 2 步（脚本），5 秒出结果
- 收到拒信想复盘 → 用第 5 节清单定位是结构/细节/匹配哪环的问题

## 2. 第一步：跑确定性审计脚本（必做，零 AI 成本）

在稿件目录执行插件自带的审计脚本：

```
python3 <插件目录>/scripts/audit/essay_audit.py --target <稿件目录>
```

稿件目录里应有：`ps-*.md`（个人陈述）、`lor-*.md`（推荐信）、`meta.json`（目标学校/项目/字数上限/匹配关键词）。

- 脚本输出 JSON（含每条发现的文件、行号、规则说明）与人类可读报告，共 32 条规则。
- 有 blocker 时脚本以非零 exit code 退出——这是设计，不是 bug。
- `--fail-on` 控制 exit code 语义：默认 `blocker`；想要更严的门禁可设为 `warning`。
- 脚本只做"机器可判定"的事：结构完整性、陈词、字数、占位符、推荐信比较级。它判定不了"故事感不感人"，那是第 5 步的事。

### 2.5 meta.json 规范

```json
{
  "target_school": "斯坦福大学",
  "target_program": "计算机科学硕士",
  "ps_word_limit": 650,
  "fit_keywords": ["李教授", "CS229"]
}
```

- `target_school` / `target_program`：STR-PS-003/004 检查 Why School/Why Major 用
- `ps_word_limit`：字数上限（默认 650），LEN-PS-001/002 用
- `fit_keywords`：目标教授/课程/实验室关键词，ADM-FIT-001 用
- 字段缺失会导致对应规则跳过（不是"通过"，是"没查"——两回事，见 STR-META-001）

规则覆盖五类：
| 类别 | 规则数 | 查什么 |
|---|---|---|
| 结构 STR-* | 11 | PS 五段（动机/反思弧线/Why School/Why Major/未来规划/结尾）、推荐信关系/联系方式/落款、meta 完整性 |
| 陈词 CLC-* | 7 | "从小就热爱"类招生官高频空话 |
| 字数 LEN-* | 4 | PS 超上限/过短、推荐信过长、超长段落 |
| 诚实 HON-* | 3 | 占位符（blocker）、绝对化表述佐证、成绩数字核对 |
| 招生官视角 ADM-* | 7 | 数字具体性、项目匹配关键词、重复用词、标点统一、第一人称 |

## 3. 第二步：分级

| 级别 | 定义 | 处理 |
|---|---|---|
| blocker | 提交后会出事：占位符未填、PS 超字数 | 必须修，不修不许提交 |
| warning | 大概率减分：缺反思弧线、缺比较级、陈词 | 本次修掉；修不掉写理由进报告 |
| nit | 洁癖项：标点混用、结尾偏弱 | 顺手修 |

分级是死的，判断是活的：如果某条 warning 在你的申请里就是致命的（如 Why School 缺失的海投嫌疑），把它升成 blocker，并在报告里写清理由。

## 4. 第三步：修复 blocker

1. blocker 逐条修，修一条跑一遍脚本确认消失。
2. 修复顺序：**诚实类先修**（占位符——这些是"正在流血"的）→ **字数类**（超字数）→ **结构类**。
3. 修不掉的 blocker：列进报告的"需人工处理"区，**不许**为了清零而删规则或改脚本�值。
4. 占位符不许豁免：必须填实，填实不了就删掉那句话。

## 5. 第四步：招生官人工评审（脚本覆盖不到的）

### 30 秒测试
- [ ] 只看第 1 段：30 秒内能说出"这个人是谁、要干什么"吗？（不能 → 钩子失败）
- [ ] 快速浏览小标题/段首句：故事线清晰吗？（段首句连起来应该能讲通故事）

### 具体性清单
- [ ] 每段至少 1 个数字（年份/人数/时长/排名），数一数
- [ ] Why School 是否点名了具体的人/课/实验室？（"排名高"不算）
- [ ] 推荐信的 2 个事例是否都有数字+比较级？

### 真诚度清单
- [ ] 有没有"正确的废话"？（删掉后信息量不变的句子）
- [ ] 反思句是否具体？（"我意识到科研需要耐心"太泛，"我意识到省略预处理步骤会让复现失败"才算）
- [ ] 读完能记住 1~2 个具体画面吗？（记不住 → 全文太平）

### 匹配度清单
- [ ] 这篇 PS 换个学校名能直接用吗？（能 → Why School 没写透）
- [ ] 未来规划与目标项目的培养方向一致吗？

### 评审输出
每项写"通过 / 不通过（原因）"，不通过的进待办，不许写"大概没问题"。

## 6. 第五步：输出报告

报告模板：

```markdown
# 自查报告：<申请人>-<目标项目>（日期）
## 结论：通过 / 不通过
## blocker（n）：已修 n，剩余 n
- [规则ID] 文件:行 —— 说明 —— 状态（已修/需人工）
## warning（n）：已修 n，豁免 n（理由）
## nit（n）
## 人工评审：30 秒测试 x/y， 具体性 x/y，真诚度 x/y，匹配度 x/y
## 需人工处理
- ...
```

报告建议存进稿件目录（如 `review-YYYYMMDD.md`），申请季复盘时对照。

## 7. 豁免规则

- 豁免只针对 warning/nit，blocker 不许豁免（占位符必须填实）。
- 豁免必须写理由 + 佐证（如"第一名已有省级证书，证书编号…"），到期复查。
- 豁免清单进报告，藏着不写等于没豁免。

## 8. 反模式

- ❌ 只跑脚本不做人工评审——脚本抓不到"故事不感人"这种问题
- ❌ 为了清零改脚本规则——这是作弊，不是自查
- ❌ 占位符靠"应该没人看出来"混过去——招生官看得出来
- ❌ "先提交了再说"——申请季没有"撤回重发"按钮
- ❌ 自查报告只写"通过"两个字——没有过程的结论不可信
- ❌ 找写稿的人自己评审——自己看自己的稿子，问题自动隐身；换独立视角

## 9. 误报处理

规则是启发式，一定会误伤。误报不可怕，乱处理才可怕：

1. **判断三问**：这段文字真的有问题吗？这条规则的本意是什么？按规则改了会不会破坏原意？
2. **确认误报**：记入报告的豁免清单并写清原因（如"'第一'指'第一次尝试'，非名次 —— 豁免 HON-ABS-001"）。
3. **拿不准**：按 warning 处理，不要直接忽略。
4. **规则本身有问题**：附最小复现文本提 issue（见第 10 节），不要自己改脚本阈值。

## 10. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 脚本是否真的跑了（而不是"我看了一遍觉得没问题"）？→ 没跑不算做。
2. blocker 是否清零或全部列入"需人工处理"？→ 有遗漏就补。
3. 人工评审清单是否逐项打勾？→ 打勾要有依据（段落号/行号）。

标准冒烟用例：对插件自带的 `fixtures/` 跑脚本，确认坏 fixture 的 blocker 全命中、好 fixture 零 blocker（见仓库根 `smoke_test.py`）。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-study-abroad/issues，正文写清"输入 → 错误输出 → 期望输出"。规则误报/漏报请附最小复现文本。
